凌晨两点，你在自己搭的服务器上巡逻
三天前种下的那排小麦，一株都没长
公屏里有人喊卡，可 CPU 才用了百分之三，却只有一个核心占满
不长和卡，看起来是两件事
它们其实通向同一个东西，每秒敲二十下的小节拍
程序转一圈，就是一次滴答，这就是“刻”
游戏里几乎所有计算，都在这一个循环里做完
一秒最多二十圈，每圈五十毫秒
你眨一次眼的功夫，它已经走了六圈
从白天到黑夜，一天是两万四千刻，现实里二十分钟
这个二十不是性能上限，是时间的定义
画面可以每秒一百多帧，逻辑还是二十步
屏幕也在跑自己的刻，那一半只管画面
那么这一圈，是谁在启动
服务端不看“跑了几圈”，它看“时间过去了多少”
每轮开始前，先给自己记一个目标时间
跑完就睡，睡到那个时间点，这叫线程睡眠
睡眠时长不是固定的，它等于五十毫秒，减去这一圈的实际耗时
所以一轮跑得越久，它能睡的时间越短
在往下走之前，先把结构摆出来
一层是外层循环，它决定什么时候跑
一层是世界更新，一圈里的全部工序
区块刻是它的子步骤，按区块重复一遍
这里藏着反直觉，一次外层循环可以跑好几个世界刻
这是补刻，不是加速，算得快就把省下的时间还给下一轮
算得慢，欠的账记在目标时间上，下一轮接着补
模拟暂停时，世界刻停下，网络和资源包继续走
所以“暂停”只停世界，不停连接
先说节奏，这些步骤绝大多数每一刻都跑一次，五十毫秒一遍
世界刻一开始，第一件事不是干活，是记账
更新刷怪统计，等于给这一圈的刷怪算配额
这一步决定你脚边的怪会不会变多
每二十刻打乱一次玩家列表，和周边区块的顺序
打乱是为了公平，免得总从同一块地开始
接着是时间管理器，昼夜、日照、天亮天黑都在这
时间每两百五十六刻同步一次，你看到的天色不是每刻刷的
然后进维度，每个维度挨个走基础更新
天气在这里推进，下雨、雷暴、雨停都算
区块生成任务也在这启动，你往前跑时，世界是这时候被造出来的
村庄和结构管理器也更新，村民的工作站点、村庄的边界
末地还多一层，龙战的数据只在末地更新
维度走完回到世界层，常加载区开始处理
常加载区给“人不在也要转”用，农场靠它
然后是玩家，出生点检查、区块加载就绪
你走到哪，世界就加载到哪，也是在这一步对齐的
接下来是实体，这一圈真正的大头
玩家的输入、碰撞、坐骑都在这处理
怪物的感知、选目标、寻路、移动，全在这一段
年龄 繁殖 呼吸 燃烧，爆炸 传送 拴绳，各类行为各跑一遍
实体走完，保存区块、回收等着清理的实体
掉线玩家的残留记录，也在这一圈清掉，不然会一直占着位置
穿过传送门的实体，不会当场搬家，先排进跨维度队列
目标维度没加载好，就下一刻再试，不是卡住，是排队
红石电路的依赖关系也在这更新，元件加了或拆了，要重新连
世界数据每三十秒存一次，按真实时间算
但区块不是到点就存，要等满一百次完整更新
官方的性能遥测，每 12000 刻发一次，也就是十分钟
最后是服务端自己的活，计分板、排队的命令
行为包的每刻函数，也在这跑，等于每刻给你一次机会
睡觉也在收尾阶段检查，所有人躺下，时间直接跳到日出
刻计数加一，这一圈才算真正走完
刚才那些步骤里，有一块是按区块重复的
区块刻就是这一步，模拟距离内每个区块都过一次
第一步刷怪，检测密度和上限，决定刷不刷、刷什么
你做的刷怪塔产量，就是这一步的产物
第二步是环境，闪电、雨雪、结冰、积雪
随机刻也挂在这一步，它是整条流水线最没规律的一步
它每刻只从区块里抓几个方块，抓到谁，谁才长
作物、草蔓延、树叶消失、铜氧化，都等这一刻
一个方块被抽中的机会是万分之六，平均要等八十二秒
第三步普通计划刻，每块每刻最多取一百条
计划刻是“约好第几刻做”的队列，发射器、投掷器、侦测器的延迟都在这
第四步随机计划刻，火、岩浆块、海带、海龟蛋走这条
两条队列各有一百条的额度，超了就排队到下一圈
一条计划刻要落地，周围那一圈的区块得先加载好，没准备好就下一圈再试
第五步给实体打标记，告诉后面的系统，这些这圈要更新
第六步更新方块实体，漏斗搬东西、熔炉烧、箱子记内容
这一步的顺序每轮都会打乱，这是基岩版红石机器不稳定的主要原因
第七步把算好的红石结果应用回方块
第八步推进保存计时，记下这个区块改过
还有一件东西，不在这条流水线里每刻算，那就是红石
它每两刻求值一次，这一刻就叫红石刻
换算成时间，一秒只有十次
求值分三步，先缓存所有元件的输入
再算信号源和电容，拉杆、按钮、火把、中继器
再算消费者和传输者，活塞、红石灯、漏斗、红石线
算完不立刻生效，先给全部元件加锁
等三步都走完，结果才一起放出去
所以同一拍里，电路看到的输入都是上一拍的
这就是“半拍”的来源，也是基岩版红石看起来怪的原因
有些方块还要检查，这一刻是不是红石刻，漏斗、比较器、活塞、钟
讲台和侦测器也在这张名单上
中继器一档仍然是两个游戏刻，两版一致
差别不在档位，在这一层加锁的结构
讲了这么多，五十毫秒到底够不够
大多数时候够，因为一圈里的活是稀疏的
不够的时候，就是卡顿
服务端先补，连跑几圈把欠的补回来
补跑的时候，你只是看到动作顿一下，而不是时间变快
只有落后超过两秒，它才放弃，一次性丢掉欠的圈数
还有一种崩法，是抛异常
与 Java 版不同，基岩版的刻流程没有异常处理兜底
发生异常直接崩，这就是基岩版做不出 Java 版那种更新抑制器的原因
唯一的例外是脚本，JS 异常不会让游戏崩
所谓优化，本质是让每一圈里要算的东西变少
比如少生成实体，别让几百个掉落物同时被算
比如把高频电路降下来，别让它每秒算十次
比如缩短模拟距离，让参与计算的区块变少
关渲染距离没用，那省的是客户端
要关的是模拟距离，那才是算力
回到那个卡顿的服务器，它站在节拍边上等一次抽签
而现在你知道，它等的是哪一拍，被谁挤掉了
